## Overview

This program demonstrates a fixed-size object pool in C using a static array and boolean allocation flags. It avoids heap allocation latency by recycling pre-allocated struct instances.

## Concepts used

- Static object pooling
- Linear search allocation ($O(N)$)
- Struct encapsulation with allocation tracking flags
- Reclaiming resources without `free()`

## How it works

1. `pool_elem_t` bundles a boolean `allocated` flag with a `pair_t obj`.
2. A static array `object_pool[10]` holds 10 pool elements.
3. `Alloc()`:
   - Scans linearly through `object_pool` from index 0 to 9.
   - Finds the first entry where `allocated == false`.
   - Marks `allocated = true` and returns a pointer to its `obj`.
   - If all slots are occupied, returns `NULL`.
4. `Free(pair_t* ptr)`:
   - Finds the enclosing element and sets `allocated = false`.

## Key excerpt

```c
typedef struct Pair {
	int first, second;
} pair_t;

typedef struct {
	bool allocated;
	pair_t obj;
} pool_elem_t;

const int POOL_SIZE = 10;
pool_elem_t object_pool[POOL_SIZE] = {0};

pair_t* Alloc() {
	for (int i = 0; i < POOL_SIZE; i++) {
		if (!object_pool[i].allocated) {
			object_pool[i].allocated = true;
			return &object_pool[i].obj;
		}
	}
	return NULL;
}
```

## Things to watch

- **Linear scan overhead**: Finding a free slot requires an $O(N)$ loop over `POOL_SIZE`. For large pools, use an embedded free-list (as demonstrated in `freelist_object_pool.c`) for $O(1)$ operations.
- **Lack of thread safety**: Concurrent calls to `Alloc` and `Free` can cause race conditions where two threads receive the same pool element; protect with a mutex if used concurrently.

## Terms

- **Object Pool**: A cache of pre-allocated objects maintained in memory to reduce allocation frequency.
