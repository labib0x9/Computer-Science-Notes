## Overview

This program demonstrates how to build an append-only binary storage manager in Go using memory-mapped files (`gommap`). It encapsulates an `*os.File` and `gommap.MMap` within a `Mapper` struct, providing a `Resize` method that expands the underlying file with `Truncate` and re-establishes the memory map as new records are appended.

## How it works

The struct `Mapper` contains `File *os.File` and `mmap gommap.MMap`.

The method `Resize(maxSize int64) error`:
- Expands file on disk using `m.File.Truncate(maxSize)`.
- Remaps the file into memory using `gommap.Map`.
- Updates `m.mmap`.

In `main`:
- Creates mapper for `"store.bin"`.
- Reads existing file size offset.
- Performs 3 successive 8-byte appends: expands size by 8 bytes via `mapper.Resize`, encodes integers `12`, `24`, and `36` into `mapper.mmap[offset:offset+8]` using `binary.BigEndian.PutUint64`, and advances `offset`.
- Iterates from start position 0 to 24, reading each 8-byte integer back via `encoder.Uint64` and logging them.

## Key excerpt

```go
func (m *Mapper) Resize(maxSize int64) error {
	if err := m.File.Truncate(maxSize); err != nil {
		return err
	}

	info, err := m.File.Stat()
	if err != nil {
		return err
	}

	mmap, err := gommap.Map(
		m.File.Fd(),
		gommap.PROT_READ|gommap.PROT_WRITE,
		gommap.MAP_SHARED,
	)
	if err != nil {
		m.File.Close()
		panic(err)
	}

	m.mmap = mmap
	return nil
}
```

## Things to watch

- **Memory unmapping leak in Resize:** In `Resize()`, a new `gommap.Map` is called without unmapping the old `m.mmap`. Over many resize operations, this leaks virtual memory mappings in the process address space. Calling `m.mmap.UnsafeUnmap()` prior to remapping is recommended.

## Terms

- **Append-only storage:** A data storage paradigm where new records are appended sequentially without modifying existing entries.
