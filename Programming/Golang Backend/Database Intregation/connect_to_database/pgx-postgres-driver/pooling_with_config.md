## Overview

This program demonstrates how to configure and use a concurrent PostgreSQL connection pool using `github.com/jackc/pgx/v5/pgxpool`. It adjusts minimum and maximum connection limits and validates safe concurrent query execution across multiple goroutines.

## Concepts used

- Synchronizing worker completion with `sync.WaitGroup`

## How it works

The program configures pool parameters:
1. `pgxpool.ParseConfig(pgURL)` parses the connection string.
2. It customizes pool thresholds:
   - `config.MinConns = 2`: Maintains at least two live connections.
   - `config.MaxConns = 10`: Limits maximum open connections to 10.
   - `config.MaxConnIdleTime = 2 * time.Minute`: Retires idle connections after 2 minutes.
3. `pgxpool.NewWithConfig` instantiates the connection pool.
4. It launches 4 concurrent worker goroutines. Each worker calls `pool.QueryRow` simultaneously.
5. Unlike single `pgx.Conn` handles, `pgxpool.Pool` checks out connections per query or handles multiplexing safely, preventing `conn busy` errors.

## Key excerpt

```go
	config, err := pgxpool.ParseConfig(pgURL)
	if err != nil {
		panic(err)
	}

	config.MinConns = 2
	config.MaxConns = 10
	config.MinIdleConns = 2
	config.MaxConnIdleTime = 2 * time.Minute

	pool, err := pgxpool.NewWithConfig(context.Background(), config)
	if err != nil {
		panic(err)
	}
	defer pool.Close()
```

## Things to watch

- **Hardcoded credentials**: The connection string contains hardcoded credentials (`short:secret`), which should be replaced by environment variables in production.
- **Resource cleanup**: Calling `defer pool.Close()` ensures all connections in the pool are closed cleanly on exit.

## Terms

- **Connection Pool**: A cache of database connections kept open so they can be reused for subsequent requests instead of creating new sockets.
- **pgxpool**: The connection pool implementation for pgx v5.
