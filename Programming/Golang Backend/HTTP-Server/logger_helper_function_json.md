## Overview

This program demonstrates manual HTTP request logging by calling a shared helper function from within individual handler bodies. It serves as a baseline comparison before refactoring logging logic into middleware.

## Concepts used

- Structured logging with `log/slog`
- Extracting request metadata (`r.Method`, `r.URL.Path`, `r.RemoteAddr`)
- Code duplication patterns in HTTP route handlers

## How it works

The code defines `loggerHelper(r *http.Request)`:
1. It reads `r.Method`, `r.URL.Path`, and `r.RemoteAddr`.
2. It outputs a structured JSON log entry via `slog.Info`.
3. Handlers `apiHandler` and `nopeHandler` manually call `loggerHelper(r)` as their first statement before performing their business logic.

In `main`, routes `/api` and `/nope` are registered with `http.HandleFunc` and served on `:8080`.

## Key excerpt

```go
func loggerHelper(r *http.Request) {
	slog.Info("request",
		"method", r.Method,
		"path", r.URL.Path,
		"remote_addr", r.RemoteAddr,
	)
}

func apiHandler(w http.ResponseWriter, r *http.Request) {
	loggerHelper(r)
	fmt.Fprintf(w, "API HANDLER")
}

func nopeHandler(w http.ResponseWriter, r *http.Request) {
	loggerHelper(r)
	fmt.Fprintf(w, "Nope Handler")
}
```

## Expected behavior (from reading the code, not run)

- Visiting `http://localhost:8080/api` outputs `API HANDLER` and logs request details to stdout.
- Visiting `http://localhost:8080/nope` outputs `Nope Handler` and logs request details to stdout.

## Things to watch

- **Maintenance overhead**: Requiring each handler to call `loggerHelper` manually leads to boilerplate code and human error when developers forget to add the helper to new endpoints.
- **Cannot measure latency**: Because the helper runs before the handler executes, it cannot record response execution time or HTTP status codes. Middleware solves this.

## Terms

- **slog**: Go standard library structured logging package introduced in Go 1.21.
