## Overview

This program demonstrates thread/goroutine starvation in Go, where a "greedy" worker monopolizes a shared mutex lock, preventing a "polite" worker from acquiring the lock and performing work.

## Concepts used

- Go mutex starvation mode vs normal mode

## How it works

1. Two goroutines compete for a single `sync.Mutex`.
2. The "greedy" worker acquires the lock, holds it for a long period, releases it briefly, and immediately attempts to re-acquire it.
3. The "polite" worker only holds the lock briefly but rarely gets a turn because the greedy worker repeatedly reacquires it.
4. Compares iteration counts between greedy and polite workers.

## Key excerpt

```go
// Greedy worker retains lock for long intervals:
greedyWorker := func() {
	defer wg.Done()
	for i := 0; i < 1000; i++ {
		mu.Lock()
		time.Sleep(3 * time.Millisecond) // monopolizes lock
		mu.Unlock()
	}
}
```

## Expected behavior (from reading the code, not run)

- Prints disproportionately higher completed iteration counts for the greedy worker.

## Things to watch

- Go's `sync.Mutex` includes an internal "starvation mode" that activates if a waiter fails to acquire the lock for more than 1 millisecond, handing lock ownership directly to the head of the wait queue.

## Terms

- **Starvation**: A condition where a concurrent process is perpetually denied access to necessary resources to make progress.
- **Mutex starvation mode**: Go runtime lock optimization that prevents tail-latency lock starvation.
