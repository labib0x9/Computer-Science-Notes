## Overview

This program demonstrates the decorator/interception pattern in Go, where a struct wraps an interface instance to inject pre- or post-processing behavior before delegating to the wrapped implementation.

## Concepts used

- Interface composition and decoration
- Custom type method receivers (`FancyName`)
- Pre-processing input parameters before delegating to nested interface components

## How it works

1. Defines `MyNewInterface` with method `Task(name string) (out string, err error)`.
2. `FancyName` implements `MyNewInterface` by prefixing a fancy title.
3. `Struct1` also implements `MyNewInterface`, but wraps an inner `mni MyNewInterface` field.
4. When `Struct1.Task` is called, it intercepts execution, sanitizes or modifies the name, and delegates to `s.mni.Task(name)`.

## Key excerpt

```go
type MyNewInterface interface {
	Task(name string) (out string, err error)
}

type FancyName string

func (f FancyName) Task(name string) (out string, err error) {
	return "Fancy Name: " + string(f) + " " + name, nil
}

type Struct1 struct {
	mni MyNewInterface
}

func (s Struct1) Task(name string) (out string, err error) {
	// Interception / validation before forwarding
	return s.mni.Task(name)
}
```

## Expected behavior (from reading the code, not run)

- Executing `Task` through `Struct1` passes through the interception layer before delegating to `FancyName`.

## Things to watch

- Interceptors allow cross-cutting concerns (logging, timing, validation, auth checks) to wrap core logic cleanly without polluting domain code.

## Terms

- **Decorator Pattern**: A structural design pattern allowing behavior to be added to an individual object dynamically without affecting other objects.
- **Interception**: Hooking into a function call to execute preparatory or concluding logic.
