## Overview

This program investigates string reallocation dynamics in Go, comparing local string header addresses against data pointers retrieved via `unsafe.StringData` during repeated concatenation.

## Concepts used

- String header memory address vs backing byte pointer
- Reallocation upon string concatenation (`temp += ...`)
- `unsafe.StringData` inspection

## How it works

1. Initializes `temp := "hello Labib"`.
2. Inspects `unsafe.Pointer(&temp)` (header location on stack) and `unsafe.StringData(temp)` (backing array).
3. Appends text: `temp += " Al"` and `temp += " Faisal"`.
4. Shows that while the header address on the stack stays fixed, the backing data pointer changes with every concatenation due to memory reallocation.

## Key excerpt

```go
temp := "hello Labib"
fmt.Println(unsafe.Pointer(&temp))
fmt.Println(unsafe.StringData(temp))

temp += " Al"
fmt.Println(unsafe.Pointer(&temp))
fmt.Println(unsafe.StringData(temp))

temp += " Faisal"
fmt.Println(unsafe.Pointer(&temp))
fmt.Println(unsafe.StringData(temp))
```

## Expected behavior (from reading the code, not run)

- The stack header address remains unchanged across all prints.
- The backing byte address updates with each concatenation, reflecting newly allocated strings.

## Things to watch

- Repeated concatenation inside tight loops creates garbage collector thrashing; `strings.Builder` should be preferred for building strings.

## Terms

- **StringData**: Built-in function `unsafe.StringData(s)` returning a pointer to the underlying byte array of string `s`.
- **String header**: A 16-byte struct (on 64-bit platforms) containing a data pointer and an integer length.
